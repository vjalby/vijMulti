# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

**vijMulti** is an R package / jamovi module dedicated to classic multivariate data analyses,
available in jamovi's **Multivariate** ribbon tab: `principal` (Principal Component Analysis),
`corresp` (Correspondence Analysis), `multcorresp` (Multiple Correspondence Analysis). It was
split out of [vijPlots](https://github.com/vjalby/vijPlots) (2026-09), which keeps the plotting
analyses and originally shipped these three as well — the code was duplicated, not moved, so
vijPlots still has its own independent copies. Discriminant Analysis (AFD) and automatic
classification (clustering) are planned future additions to this module.

### Target jamovi version

Targets jamovi's **current** channel (28.2), same as vijPlots. As of jamovi 28.1, the bundled
`jmvcore` no longer calls the deprecated `ggplot2::element_line(size = ...)`, so the "The `size`
argument of `element_line()` is deprecated" warning should not appear — if it does, treat it as a
real regression, not a known non-issue.

## Commands

```r
devtools::load_all(".")                                   # load the package for interactive dev
devtools::document()                                       # regenerate man/ from roxygen comments — stubs only, not actively maintained
jmvtools::prepare()                                         # regenerate R/*.h.R and jamovi/0000.yaml from jamovi/*.yaml after editing options
jmvtools::install()                                         # build & install the .jmo into a local jamovi (requires options(jamovi_home=...), see .Rprofile)
```

`jamovi_home` is set via a project-local `.Rprofile` (gitignored, copied by hand between machines
— see vijPlots' equivalent note). `inst/` and `R/*.h.R` are build-generated by `jmvtools::prepare()`/
`jmvtools::install()`; don't fuss over preserving uncommitted changes under `inst/` before running
either — `prepare()` can delete files there outright as part of its regeneration pass.

`jmvtools::prepare()` also re-syncs each analysis's `menuGroup`/`category` in `jamovi/0000.yaml`
from that analysis's own `jamovi/<name>.a.yaml` header — hand edits to those fields in `0000.yaml`
get silently overwritten on the next `prepare()`. Edit the `.a.yaml` header instead. Note that the
per-analysis `category:` field in `.a.yaml` is a fixed jamovi-internal enum (`analyses` or `plots`
only — nothing else validates), unrelated to which ribbon tab the module appears under; the ribbon
tab is controlled by `jamovi/0000.yaml`'s top-level `category:` (currently `multivariate`) plus
each analysis's `menuGroup: vijMulti`. Leaving the per-analysis `.a.yaml` `category:` unset
defaults to `analyses`, which is what puts these three under jamovi's **Analyses** grouping rather
than looking like plots.

Testing (testthat edition 3, run from the package root after `devtools::load_all(".")`):

```r
Sys.setenv(NOT_CRAN = "true")                              # required, see "Testing" below
testthat::test_file("tests/testthat/test-principal.R")
testthat::test_dir("tests/testthat")
```

There is no CI workflow in this repo (no `.github/`) and no `renv`/`air.toml`.

## Architecture

### Five files per analysis

Each analysis `<name>` (`principal`, `corresp`, `multcorresp`) is defined by:

- `R/<name>.b.R` — the backend, an R6 class `<name>Class` (`inherit = <name>Base`) implementing
  `private$.init()`, `private$.run()` (validates required variables, prepares data, calls
  `image$setState(...)`), and `private$.plot(image, ggtheme, theme, ...)`.
- `R/<name>.h.R` — **auto-generated by `jmvtools::prepare()`; never edit by hand.**
- `jamovi/<name>.a.yaml` / `.u.yaml` / `.r.yaml` — option definitions, UI layout, result items.

All three are registered in `jamovi/0000.yaml` (`ns: vijMulti`, `menuGroup: vijMulti`,
`menuSubgroup: Multivariate`) and in `jamovi/00refs.yaml` (citations: `factominer`, `psych`,
`greenacre`, `gpa` — only the subset actually referenced by these three analyses' `.r.yaml` files,
trimmed down from vijPlots' full reference list).

### Shared utilities (`R/utils.R`)

Copied in full from vijPlots (all functions are used by at least one of the three analyses), all
prefixed `vij*`: `vijColorScale()`/`vijColorPalette()`/`vijColorPaletteNlevels()`/
`vijOneColorOfPalette()` build palette scales from the `colorPalette` option; `vijVar()` wraps an
optional `rlang::sym`-or-`NULL`; `vijTitlesAndLabels()`/`vijTitleAndLabelFormat()` build `labs()`
and axis/legend theme; `vijHelpMessage()`/`vijErrorMessage()`/`vijWarningMessage()`/
`vijDebugMessage()` write to `self$results$todo`; `vijDebugPlot(self, plot)` — called at the end of
every `.plot()` — forces an eager build to surface any ggplot2 warning/message as a Notice instead
of letting jmvcore silently swallow it (only active when `DESCRIPTION`'s `Version` has a 4th
component, e.g. `0.0.1.0` — no-op on a plain `x.y.z` release version; it checks
`utils::packageVersion("vijMulti")` specifically, so this string must stay in sync if the package
is ever renamed again).

### Non-obvious runtime gotchas

These are the ones from vijPlots' own notes confirmed to actually apply to `principal`/`corresp`/
`multcorresp` (see vijPlots' `CLAUDE.md` for the full list, most of which concerns analyses that
don't exist in this module):

- Keep validation and expensive/one-off computation in `.run()`, not `.plot()` — `.plot()` can be
  invoked multiple times per run (resizing, re-render), `.run()` only once, cached via
  `image$setState(...)`.
- `jmvcore::select(df, character(0))` errors on the currently installed `jmvcore`, crashing inside
  the base `Analysis$init()` before a module's own "no variable selected" guard in `.run()` is ever
  reached. Don't write zero-variable tests that go through a full `analysis$run()`/wrapper call.
- The generated `<name>(...)` wrapper's `for (v in ...)` loops (over `rows`/`cols`/`rowLabels` in
  `corresp`, `vars`/`supplVars` in `multcorresp`, `groupVar` in `principal`) are only safe to omit
  in a direct `data=` call because every one of those options already has an explicit `default:` in
  its `.a.yaml` (so the generated argument defaults to `NULL`) — an option added later without a
  `default:` would reintroduce the "argument is missing, with no default" crash. Check a new
  option's generated `.h.R` signature before writing its test.
- `jmvcore::Analysis$.render()` wraps rendering in `suppressWarnings(suppressMessages(...))`,
  silently swallowing ggplot2 diagnostics (including `message`-class `cli_inform()` ones like
  "Ignoring unknown labels"). `vijDebugPlot()` (see above) is the workaround for surfacing these
  during testing.
- `vijTitlesAndLabels()`'s optional `plot` argument lets it inspect which of `fill`/`colour`/
  `shape` are actually mapped (minus each layer's `aes_params`) so it only sets a legend title for
  aesthetics really present — skipping this risks ggplot2's "Ignoring unknown labels" diagnostic.
- Never build a formula by pasting/`reformulate()`-ing a raw jamovi variable name into text — a
  name with a space or `!+?%-`/backtick breaks `stats::reformulate()`/`as.formula()` at parse time.
  `corresp.b.R` uses `jmvcore::composeFormula('.COUNTS', c(rowVarName, colVarName))` instead, which
  backtick-escapes each component correctly.
- Prefer a `switch()` over `do.call(getFromNamespace(...), ...)` for dispatching on an option value
  — `principal.b.R`'s rotation option calls `GPArotation::Varimax()` etc. directly in a `switch()`,
  keeping every callable function grep-visible.
- `Table$setNote(key, NULL)` doesn't reliably clear a previously-shown note on a `rows: 0` table
  when a `reject()`-interrupted run leaves an unguarded `setNote()` call unreached — root-caused and
  fixed for `corresp`'s `eigenvalues`/`chisq` note (`rows: 1` + explicit `deleteRows()`; see
  `corresp.b.R`'s `.run()`). `multcorresp.b.R` has the same *unfixed* pattern on `eigenvalues`'s
  `'method'`/`'adjusted'` notes, `discrim`'s `'sup'` note, `categories`'s `'normalization'`/`'sup'`
  notes, and `observations`'s `"100"`/`'normalization'` notes — left unfixed on the same basis as
  vijPlots (narrow repro surface, and the real fix belongs upstream in jmvcore/jamovi).

### Translations (`jamovi/i18n/*.po`)

`fr.po` was seeded from vijPlots' translations (325 of 333 strings reused via exact `msgid` match)
and completed by hand for the handful of vijMulti-specific strings (package title/description,
dataset descriptions, and the three long analysis help texts, which differ from vijPlots' only in
the "Data Library > vijMulti > ..." line). Regenerate via `jmvtools::i18nUpdate("fr")` /
`jmvtools::i18nUpdate("catalog")` after editing `.a.yaml`/`.u.yaml`/`.b.R` strings — same exact-
string-match caveat as vijPlots applies (a new option reusing a common short string silently
inherits whatever translation that string already has elsewhere).

## Testing

Same two-level pattern as vijPlots: **state checks** (call the wrapper, assert on
`results$plot$state`) and **visual snapshots** (`expect_plot_snapshot()`, defined in
`tests/testthat/helper-vdiffr.R`, calling `vdiffr::expect_doppelganger()` locally and skipping the
pixel diff — but still smoke-testing the render — when `CI` is truthy). Requires
`Sys.setenv(NOT_CRAN = "true")` locally or snapshot checks silently skip. Review new/changed
snapshots with `testthat::snapshot_review("<name>")`.

## Icon

`icon/vijMulti.svg` (viewBox `0 0 74 44`, matching vijPlots' icon dimensions): a factorial-map/
biplot motif — two grey axes crossing at the origin, two `#e6ac40` (jamovi's own icon yellow, seen
across its built-in analysis icons) variable vectors, and a scatter of blue observation points —
evoking the 2D map that all three analyses produce, rather than a generic pictogram.
