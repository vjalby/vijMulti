# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

**vijMulti** is an R package / jamovi module dedicated to classic multivariate data analyses,
available in jamovi's **Analyses** ribbon tab, under its own `vijMulti` menu (subgroup
"Multivariate"): `principal` (Principal Component Analysis),
`corresp` (Correspondence Analysis), `multcorresp` (Multiple Correspondence Analysis). It was
split out of [vijPlots](https://github.com/vjalby/vijPlots) (2026-09), which keeps the plotting
analyses and originally shipped these three as well — the code was duplicated, not moved, so
vijPlots still has its own independent copies. Discriminant Analysis (AFD) and automatic
classification (clustering) are planned future additions to this module.

### Target jamovi version

Targets jamovi's **current** channel (28.2), same as vijPlots. As of jamovi 28.1, the bundled
`jmvcore` no longer calls the deprecated `ggplot2::element_line(size = ...)`, so the "The `size`
argument of `element_line()` is deprecated" warning should not appear — if it does, treat it as a
real regression, not a known non-issue.

## Commands

```r
devtools::load_all(".")                                   # load the package for interactive dev
devtools::document()                                       # regenerate man/ from roxygen comments — stubs only, not actively maintained
jmvtools::prepare()                                         # regenerate R/*.h.R and jamovi/0000.yaml from jamovi/*.yaml after editing options
jmvtools::install()                                         # build & install the .jmo into a local jamovi (requires options(jamovi_home=...), see .Rprofile)
```

`jamovi_home` is set via a project-local `.Rprofile` (gitignored, copied by hand between machines
— see vijPlots' equivalent note). `inst/` and `R/*.h.R` are build-generated by `jmvtools::prepare()`/
`jmvtools::install()`; don't fuss over preserving uncommitted changes under `inst/` before running
either — `prepare()` can delete files there outright as part of its regeneration pass.

`jmvtools::prepare()` also re-syncs each analysis's `menuGroup`/`category` in `jamovi/0000.yaml`
from that analysis's own `jamovi/<name>.a.yaml` header — hand edits to those fields in `0000.yaml`
get silently overwritten on the next `prepare()`. Edit the `.a.yaml` header instead. Note that the
per-analysis `category:` field in `.a.yaml` is a fixed jamovi-internal enum (`analyses` or `plots`
only — nothing else validates). It does pick the ribbon tab: unset, it defaults to `analyses`,
which puts these three in jamovi's **Analyses** tab (checked in jamovi 28.17, 2026-11-21), as a
`vijMulti` menu button (`menuGroup`) whose entries are listed under "Multivariate"
(`menuSubgroup`). `jamovi/0000.yaml`'s top-level `category: multivariate` does *not* choose the
tab (the module shows under Analyses with it); its effect, probably the module's category in the
jamovi library, was not checked.

Testing (testthat edition 3, run from the package root after `devtools::load_all(".")`):

```r
Sys.setenv(NOT_CRAN = "true")                              # required, see "Testing" below
testthat::test_file("tests/testthat/test-principal.R")
testthat::test_dir("tests/testthat")
```

There is no CI workflow in this repo (no `.github/`) and no `renv`/`air.toml`.

## Architecture

### Five files per analysis

Each analysis `<name>` (`principal`, `corresp`, `multcorresp`) is defined by:

- `R/<name>.b.R` — the backend, an R6 class `<name>Class` (`inherit = <name>Base`) implementing
  `private$.init()`, `private$.run()` (validates required variables, prepares data, calls
  `image$setState(...)`), and `private$.plot(image, ggtheme, theme, ...)`.
- `R/<name>.h.R` — **auto-generated by `jmvtools::prepare()`; never edit by hand.**
- `jamovi/<name>.a.yaml` / `.u.yaml` / `.r.yaml` — option definitions, UI layout, result items.

All three are registered in `jamovi/0000.yaml` (`ns: vijMulti`, `menuGroup: vijMulti`,
`menuSubgroup: Multivariate`) and in `jamovi/00refs.yaml` (citations: `capackage`,
`greenacre`, `gpa` — only the subset actually referenced by these three analyses' `.r.yaml` files,
trimmed down from vijPlots' full reference list).

### Shared utilities (`R/utils.R`)

Copied from vijPlots (see the end of this section), all prefixed `vij*`: `vijColorScale()`/`vijColorPalette()`/`vijColorPaletteNlevels()`/
`vijOneColorOfPalette()` build palette scales from the `colorPalette` option; `vijVar()` wraps an
optional `rlang::sym`-or-`NULL`; `vijTitlesAndLabels()`/`vijTitleAndLabelFormat()` build `labs()`
and axis/legend theme; `vijHelpMessage()`/`vijWarningMessage()`/`vijDebugMessage()` insert a
Notice/Html item at the top of `self$results` (`vijErrorMessage()` calls `jmvcore::reject()`, which
stops the analysis); `vijDebugPlot(self, plot)` — called at the end of every `.plot()` — forces an
eager build to surface any ggplot2 warning/message as a Notice instead of letting jmvcore silently
swallow it (only active when `DESCRIPTION`'s `Version` has a 4th component, e.g. `0.0.1.0` — no-op
on a plain `x.y.z` release version; the package is found via `utils::packageName()`).

`vijLabelNA(self)` (from vijPlots, 2026-11-08) returns a labelling function showing `NA` as
`"(Missing)"` (fr "(Manquant)"). Used only for PCA's group variable: its legend (through the
`labels` argument of `vijColorScale()`) and the Observations table's Group column. The real `NA`
stays in the plot state, labelled at plot time (so in the current language, as in vijPlots).
Deliberately not used for a missing *label* (PCA/MCA `labelVar`): the point is left without a text
label, rather than showing several identical "(Missing)" labels (user's choice, 2026-11-08).
The observation text layers have `na.rm = TRUE`, so a missing label just drops that text, without
ggplot2's "Removed 1 row containing missing values" warning (surfaced by `vijDebugPlot()` in dev
versions) — the same mechanism as vijPlots' `piechart`/`barplot` hidden labels.
Since 2026-11-22, `R/utils.R` and `tests/testthat/test-utils.R` are **exact copies** of vijPlots'
(edited there, copied here; vijPlots' `build.R` checks they are identical): don't edit them here
alone. Some of their helpers are unused here (`vijVar()`, `vijOneColorOfPalette()`,
`vijFormatCount()`, `lastColor` of `vijColorScale()`): keep them. The vijPlots-only helpers
(`vijGridLines()`, `vijHideAxis()`, `vijNudgePosition()`) are in vijPlots' `R/utilsPlots.R`, not copied.

### Theme and font options (ported from vijPlots, 2026-11-21)

Same `plotTheme`/`fontFamily` options, values and "Theme" UI section as vijPlots (see its
`CLAUDE.md`, "Appearance options", for the reasoning: theme list, `base_size = 16`, margins, SPSS
`suppressWarnings()`, why every text layer needs `family =`). The section comes right after "Plot
Titles & Subtitles" (before PCA's "Advanced Options" and MCA's "Save"). Every plot adds
`ggtheme + vijPlotTheme(self$options)`, scree and discrimination plots included, and every text
layer gets `family = fontFamily` (`vijFontFamily(self$options)`): 3 in PCA, 1 in CA, 4 in MCA
(its `geom_text` fallback when `ggrepel` is off included). A new text layer must get it too: each
analysis' "theme and font family" test checks every text layer (`helper-theme.R`). Both options are
in every Image's `clearWith:` (jamovi only re-renders an image whose `clearWith` changed).

vijMulti-specific: the factorial maps' forced black frame (`panel.border` black, linewidth 1, no
`axis.line`) is kept with "Default" and the four jamovi themes (so the default look, snapshots
included, is unchanged), but skipped with the four ggplot2 themes (`startsWith(plotTheme, "gg")`),
which keep their own frame (Light's gray one, Bw/Linedraw's dark one) or, for Dark, no frame on a
filled panel. No grid options here, so `vijGridLines()` is still not needed: ggplot2's themes and
jamovi's Hadley/Minimal bring their grid, the others have none.

### CA/MCA backends (`ca` package)

Both analyses use Greenacre's `ca` package (FactoMineR was dropped in 1.1.0: lighter module, and
FactoMineR 2.16 silently truncates `$eig` to `ncp` eigenvalues). `corresp`'s `.ca()` wraps
`ca::ca()`, `multcorresp`'s `.mca()` wraps `ca::mjca()` (always pass `lambda` explicitly: its
default is `"adjusted"`). Both return all rows/categories together, in data order, with `NA`
mass/contributions/inertia for supplementary points. Axis signs follow a fixed rule: on each axis,
the active column (CA) or active category (MCA) farthest from the origin is positive. `mjca`
pitfalls: in indicator mode, `colpcoord`/`colcor` of supplementary categories are computed from
Burt profiles, so `.mca()` uses `colcoord × sv` and `coord² / (n/n_c − 1)` instead; in Burt mode,
`rowctr`/`rowcor` are `NA`. Burt observation coordinates follow Stata's convention (indicator
standard coordinates), not the supplementary projection of `ca`/FactoMineR.

### Non-obvious runtime gotchas

These are the ones from vijPlots' own notes confirmed to actually apply to `principal`/`corresp`/
`multcorresp` (see vijPlots' `CLAUDE.md` for the full list, most of which concerns analyses that
don't exist in this module):

- Keep validation and expensive/one-off computation in `.run()`, not `.plot()` — `.plot()` can be
  invoked multiple times per run (resizing, re-render), `.run()` only once, cached via
  `image$setState(...)`.
- `jmvcore::select(df, character(0))` errors on the currently installed `jmvcore`, crashing inside
  the base `Analysis$init()` before a module's own "no variable selected" guard in `.run()` is ever
  reached. Don't write zero-variable tests that go through a full `analysis$run()`/wrapper call.
- Variable/Variables options have no `default:` in their `.a.yaml`, so the generated `<name>(...)`
  wrapper has no default for them either: a direct `data=` call (e.g. in tests) must pass every one
  of them, using `NULL` for the unused ones (e.g. `corresp(..., rowLabels = NULL, columns = NULL)`
  in `obsTable` mode), or it fails with "argument is missing, with no default".
- `jmvcore::Analysis$.render()` wraps rendering in `suppressWarnings(suppressMessages(...))`,
  silently swallowing ggplot2 diagnostics (including `message`-class `cli_inform()` ones like
  "Ignoring unknown labels"). `vijDebugPlot()` (see above) is the workaround for surfacing these
  during testing.
- `vijTitlesAndLabels()`'s optional `plot` argument lets it inspect which of `fill`/`colour`/
  `shape` are actually mapped (minus each layer's `aes_params`) so it only sets a legend title for
  aesthetics really present — skipping this risks ggplot2's "Ignoring unknown labels" diagnostic.
- Never build a formula by pasting/`reformulate()`-ing a raw jamovi variable name into text — a
  name with a space or `!+?%-`/backtick breaks `stats::reformulate()`/`as.formula()` at parse time.
  `corresp.b.R` uses `jmvcore::composeFormula('.COUNTS', c(rowVarName, colVarName))` instead, which
  backtick-escapes each component correctly.
- Prefer a `switch()` over `do.call(getFromNamespace(...), ...)` for dispatching on an option value
  — `principal.b.R`'s rotation option calls `GPArotation::Varimax()` etc. directly in a `switch()`,
  keeping every callable function grep-visible.
- `corresp`'s `contingency`/`rowProfiles`/`colProfiles` tables deliberately get their columns and
  rows in `.run()`, not `.init()` (unlike the Row/Column Summary tables): the contingency table's
  column type (`integer` vs `number`) is decided from the actual count values — a `number` column
  displays integers as `12.00`, and the Counts/jamovi-weights column type isn't a reliable proxy —
  in contTable mode the rows come from the Row Labels values, and the `*` supplementary marks need
  the supplementary options validated (via `reject()`) first. Moving only part of it to `.init()`
  would add duplicated validation for a brief cosmetic gain on tables that are off by default.
  Reviewed and declined (2026-09); don't reopen without a new argument.
- `Table$setNote(key, NULL)` doesn't reliably clear a previously-shown note on a `rows: 0` table
  when a `reject()`-interrupted run leaves an unguarded `setNote()` call unreached — root-caused and
  fixed for `corresp`'s `eigenvalues`/`chisq` note (`rows: 1` + explicit `deleteRows()`; see
  `corresp.b.R`'s `.run()`). `multcorresp.b.R` has the same *unfixed* pattern on `eigenvalues`'s
  `'method'` note, `discrim`'s `'sup'` note, `categories`'s `'normalization'`/`'sup'`
  notes, and `observations`'s `"100"`/`'normalization'` notes — left unfixed on the same basis as
  vijPlots (narrow repro surface, and the real fix belongs upstream in jmvcore/jamovi).
- No ggpp nor ggforce (dropped 2026-11-21, as in vijPlots: ggpp alone pulled lubridate,
  timechange, xts and polynom into the .jmo, ~2.2 MiB of 5.3 MiB). PCA's variable labels are
  nudged away from the origin with per-label `nudge_x`/`nudge_y` in `geom_text_repel()` (identical
  to `ggpp::position_nudge_center()`, except a variable exactly at the origin is no longer nudged);
  the unit circle is a `geom_polygon()` on 721 points with `lineend = "round"`, giving the same SVG
  as `ggforce::geom_circle(n = 720)`. Rebuild the .jmo from an emptied `build/R*` directory,
  or the old packages stay in it.

### Numerical thresholds (settled 2026-11-16 — read before reporting a "noise vs tiny real value" finding)

Several checks separate rounding noise (~`eps` = 2.2e-16, relative) from a tiny but real value.
Whatever the threshold, a dataset can always be built that falls on the wrong side of it, so an
audit hunting for such cases finds new ones indefinitely: each fix only moves the boundary. The
rule: **a finding of this kind is only worth fixing if it is reached with realistic data** (a Total
row, 200 variables, a factorial design — not scales nine orders of magnitude apart, nor counts
multiplied by 1e-18). Otherwise leave the code alone.

Current thresholds, all deliberate:

- Null axes: PCA `sdev > sqrt(eps) * sdev[1]`, CA `sv > sqrt(eps)`, MCA
  `lambdaI > sqrt(eps) * lambdaI[1]`. Conservative on purpose — refusing a real but negligible
  axis only costs a message, whereas accepting a noise axis gives arbitrary standard scores (the
  bug fixed in `fa5f4e5`). Don't lower them to `100 * eps`.
- PCA correlation matrix: *singular* = `solve()` fails (one diagnosis in `.run()`, shared by the
  warning and the KMO table, whose two rows are then left empty); *nearly singular* =
  `rcond < sqrt(eps)`, warning only.
- Points/values at an exact degeneracy, where the statistic would be noise / noise, are left
  empty below `100 * eps`: CA cos²/QLT of a point at the centroid (distance to the centroid), PCA
  KMO of uncorrelated variables (largest off-diagonal correlation). Measured for CA: cos² is
  accurate to 3 decimals down to a distance of ~1e-14, meaningless below 1e-15 — `sqrt(eps)` was
  tried first and wrongly emptied valid cos² at 8e-10.
- PCA KMO and Bartlett's test are computed in `principal.b.R` (`.kmo()`, `.bartlett()`), not by
  psych: Bartlett from the log-determinant (`det()` underflows to 0 with ~200 variables), KMO from
  the inverse already computed for the singularity diagnosis.

Reported and deliberately left as is (unrealistic data):

- PCA, unstandardized: two variables whose standard deviations differ by 1e9 — the second axis
  (1e-18 of the variance) is declared null and the analysis rejected.
- CA: all counts multiplied by 1e-18 — rejected by the absolute test `chisq <= eps`.
- MCA, Burt method: supplementary categories exactly at the centroid (a supplementary variable
  exactly independent of every active one) show a cos²/QLT made of rounding noise.
- MCA, Benzécri/Greenacre corrections with exactly independent active variables: the test
  `sqrt(eig) <= 1/p` has no tolerance, hence a 100 % axis (Benzécri) or an infinite percentage
  (Greenacre).

The last two only arise with a balanced design built on purpose; reopen them if such data become
a real use case (the fix would be two more `100 * eps` guards).

### Translations (`jamovi/i18n/*.po`)

`fr.po` was seeded from vijPlots' translations (325 of 333 strings reused via exact `msgid` match)
and completed by hand for the handful of vijMulti-specific strings (package title/description,
dataset descriptions, and the three long analysis help texts, which differ from vijPlots' only in
the "Data Library > vijMulti > ..." line). Regenerate via `jmvtools::i18nUpdate("fr")` /
`jmvtools::i18nUpdate("catalog")` after editing `.a.yaml`/`.u.yaml`/`.b.R` strings — same exact-
string-match caveat as vijPlots applies (a new option reusing a common short string silently
inherits whatever translation that string already has elsewhere).

## Testing

Same two-level pattern as vijPlots: **state checks** (call the wrapper, assert on
`results$plot$state`) and **visual snapshots** (`expect_plot_snapshot()`, defined in
`tests/testthat/helper-vdiffr.R`, calling `vdiffr::expect_doppelganger()` locally and skipping the
pixel diff — but still smoke-testing the render — when `CI` is truthy). Requires
`Sys.setenv(NOT_CRAN = "true")` locally or snapshot checks silently skip. Review new/changed
snapshots with `testthat::snapshot_review("<name>")`.

`vdiffr` is used by the tests but deliberately left out of `DESCRIPTION`'s `Suggests` (2026-11-21):
the jamovi compiler installs Suggests as well as Imports into `build/R*` and the .jmo, and vdiffr
(not shipped with jamovi) made the .jmo 0.24 MiB heavier (1.91 vs 1.67 MiB). It must be installed by hand in
the dev library; `expect_plot_snapshot()` skips when it is missing. Don't add it back.

(jamovi's module menu-icon procedure, 2026-11; the key must match the analyses' `menuGroup`

axes, two orange variable vectors, five white-filled blue observation points), the 2D map all
three analyses produce.
